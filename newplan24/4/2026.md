# Stabilization & Refinement Execution Plan
**Project:** Found 404 — Cybersecurity Orchestration Platform
**Date Issued:** 2026-04-24
**Scope:** Stabilization / Refinement ONLY — No new features
**Personas Applied:** Lead Full-Stack Engineer · Senior Penetration Tester · Expert UI/UX Dashboard Designer · Professional Security Auditor

---

## 0. Guiding Constraints (Read Before Executing Any Phase)

1. **NO new features.** Every task in this plan must terminate in one of: (a) bug fix, (b) UX refinement of an existing screen, (c) data-pipeline correction, (d) isolation/hardening of existing infrastructure, (e) audit / verification artifact. If a task starts drifting into "we should also add X," stop and mark it out of scope.
2. **No regressions.** Each phase ends with a regression pass: login → dashboard → scan → history → vulnerabilities → report.
3. **Evidence first, change second.** Every refactor must be preceded by a reproducible log / screenshot / network trace captured in `/evidence/<phase>/<task>/`.
4. **Two-tier acceptance.** Each task has (a) functional acceptance (it works) and (b) professional-standard acceptance (it matches the industry baseline identified in Phase 1).
5. **Isolation is inviolable.** No task in any phase may weaken the lab's network isolation guarantees. If a task requires relaxing isolation to reproduce a bug, restore isolation before closing the task.

## Phase 1 — Research & Baseline Audit (foundational; do not skip)

**Objective:** Establish the professional baseline against which every subsequent change is measured. Output is a written baseline document, not code changes.

### 1.1 Industry Standards Research (time-boxed)

Produce a single `/docs/audit/baseline_2026-04-24.md` capturing the following, with citations:

1. **Full-Stack QA & Backend→Frontend Pipelines**
   - ISTQB end-to-end testing taxonomy (unit → integration → contract → E2E → exploratory).
   - Contract-testing pattern (OpenAPI schema as the single source of truth between FastAPI and the React client).
   - WebSocket / SSE reliability patterns: heartbeat, reconnect-with-backoff, resume-from-sequence.
   - Observability triad applicable here: structured logs (JSON), request-id propagation, RED metrics (Rate / Errors / Duration) per endpoint.

2. **Cybersecurity Dashboard UI/UX**
   - Mitre ATT&CK Navigator, Elastic Security, Wazuh, OpenVAS GSA — what they do well, what they do badly.
   - NIST SP 800-160 Vol 2 and NN/g's cognitive-load research applied to SOC dashboards.
   - Alert-fatigue literature (Ban & Heartfield, Verizon DBIR operational-fatigue data): deduplication, severity-tiered color palette (avoid rainbow), progressive disclosure, density tiers (comfortable / compact).
   - Accessibility baseline: WCAG 2.2 AA, 4.5:1 contrast, keyboard-only navigation.

3. **Isolated Pentest Lab SOPs**
   - OffSec / SANS GPEN guidance on isolated lab construction.
   - Docker network isolation primitives: `internal: true` networks, no bridge-to-host, `iptables` egress deny-all with allowlist, DNS scoping.
   - Reference architectures: HackTheBox, TryHackMe, OWASP WebGoat deployment patterns.

4. **Vulnerability Management & Scanner-Accuracy Auditing**
   - CVSS 3.1/4.0 scoring normalization; EPSS for exploit likelihood.
   - Golden-dataset approach: a fixed set of CVEs intentionally planted in the lab, each with known CVE-ID + CWE + expected detection signature.
   - True-positive / false-positive / false-negative matrix; precision/recall targets (industry baseline ≥ 0.90 recall on planted criticals).

### 1.2 Current-State Snapshot Audit

Run each in order; capture output under `/evidence/phase1/`:

Cross-reference against [frontend/src/api](frontend/src/api) and [frontend/src/services](frontend/src/services) consumers. Flag orphaned endpoints (no consumer) and orphaned consumers (no endpoint).

4. **Service inventory** — [backend/app/services](backend/app/services) — for each service (`scan_tasks`, `nuclei_wrapper`, `nmap_wrapper`, `openvas`, `validation_probe`, `finding_dedup`, `unified_risk_engine`, `scope_guard`, `lab_manager`, `ws_manager`), document: owner endpoint, execution path (sync vs Celery vs thread), data it writes, screen that renders its output.

## Phase 2 — End-to-End Functional Validation (Backend ↔ Frontend Pipeline)

**Objective:** Prove that every datum produced by the backend reaches the correct UI element with the correct type, ordering, and freshness guarantees. No data loss, no UI errors, no silent truncation.

### 2.1 Contract Lock

1. Export the live OpenAPI spec from FastAPI (`/openapi.json`) to `/docs/contracts/openapi_2026-04-24.json`.
2. Generate a typed client (openapi-typescript or openapi-fetch) into `frontend/src/api/generated/`. Do **not** replace existing call sites yet — this is a reference for drift detection.
3. Diff generated types against the hand-written ones currently in [frontend/src/api](frontend/src/api). Every mismatch becomes a task in 2.2.

### 2.2 Route-by-Route Validation

For each route identified in 1.2.1, run this checklist:

- [ ] Happy path request returns 2xx with payload matching Pydantic schema.
- [ ] Error paths (401/403/404/422/500) each return the documented error envelope — not a stack trace, not an HTML page.
- [ ] Field naming is consistent snake_case on the wire; frontend converts at the boundary, not ad hoc.
- [ ] Timestamps are ISO 8601 UTC with `Z` suffix; frontend renders in user locale.
- [ ] Pagination envelope is uniform (`{items, total, page, page_size}` — pick one shape and enforce it).
- [ ] Numeric precision is preserved (CVSS 9.8 must not become 9.800000001 or 9).
- [ ] Empty-state: backend returns `[]` (not `null`), frontend renders empty-state component (not blank box, not error).

### 2.3 Real-Time Channel Validation

Audit [backend/app/services/ws_manager.py](backend/app/services/ws_manager.py) and [backend/app/services/event_publisher.py](backend/app/services/event_publisher.py):

- [ ] WebSocket reconnects with exponential backoff; documented maximum interval.
- [ ] Messages carry monotonic sequence numbers; the client rejects out-of-order.
- [ ] Heartbeat every N seconds; disconnect detected within 2× heartbeat.
- [ ] Backpressure: if the client is slow, messages coalesce (latest-wins for status, append-only for events).
- [ ] All WS events are also retrievable via REST so a late-joining client can catch up.

### 2.4 E2E Regression Suite (existing only — no new features)

Inside [frontend/src/tests](frontend/src/tests) and [backend/tests](backend/tests), ensure these flows have at least one automated E2E:

1. Login → token stored → protected route reachable.
2. Launch scan (via existing scan screen) → task enqueued → WS progress events → completion → result visible on History.
3. Click vulnerability row → detail modal populates all documented fields.
4. Generate report (existing `ReportGenerator.jsx`) → PDF downloads → opens without corruption.
5. Logout → token cleared → protected route redirects.

### 2.5 Observability Sanity Check

- [ ] Each API request has a `request_id` propagated into logs and returned in response header.
- [ ] `structlog` (or equivalent) JSON logs at INFO for all state-changing endpoints.
- [ ] A single trace can be followed from button-click in the browser console → nginx → FastAPI → Celery worker → DB.

**Phase 2 Exit Criteria**
- [ ] OpenAPI contract locked and committed.
- [ ] Zero orphaned endpoints, zero orphaned consumers.
- [ ] Contract-diff task list closed (all blockers resolved).
- [ ] E2E regression suite green on CI.
- [ ] One trace captured end-to-end and stored under `/evidence/phase2/trace_sample.log`.

## Phase 3 — Scan Screen UI/UX Rebuild (Refinement, not new features)

**Objective:** Redesign the existing manual-scan interface into an intuitive, professional-grade configuration surface. All configuration options must map to existing backend capabilities — no new knobs.

### 3.1 Heuristic Audit of the Current Scan Screen

Walk the current scan screen component tree. Score each against NN/g's 10 heuristics and Shneiderman's 8 golden rules. Capture findings in `/evidence/phase3/heuristic_audit.md`.

Focus specifically on:
- Visibility of system status (is the user ever unsure if a click did something?).
- Match between system and real world (are labels written in pentester vocabulary or CRUD vocabulary?).
- Error prevention (can a user launch a scan against an out-of-scope target? — must be blocked by `scope_guard`, not just hoped against).
- Recognition over recall (does the user have to remember the previous target, or is it offered?).

### 3.2 Information Architecture (wireframe only — no code yet)

Produce wireframes (Figma or Markdown ASCII) for the rebuilt scan screen with this IA:

```
[ Scan Configuration ]
├── 1. Target            (presets from lab inventory + manual entry, validated by scope_guard)
├── 2. Scan Profile      (Quick / Standard / Deep — each maps to an existing backend preset)
├── 3. Advanced (collapsed by default)
│   ├── Port range
│   ├── Nuclei templates (checkbox tree, grouped by severity)
│   ├── Rate limiting
│   └── Auth (existing credentials pickers only)
├── 4. Scheduling        (Run now / Scheduled — existing scheduler only)
└── 5. Review & Launch   (human-readable summary of every choice)
```

Principles enforced:
- **Progressive disclosure.** Advanced settings collapsed by default; 80% of users never open them.
- **Single primary action.** One "Launch Scan" button, visually dominant; secondary "Save as Template" de-emphasized.
- **Inline validation.** Target field validates synchronously against scope list; invalid state is non-blocking (shows hint) until submit.
- **Preview before launch.** Step 5 shows the exact backend call that will be made (command preview) — auditable, learnable.

### 3.3 Implementation (refactor existing component only)

- [ ] Replace the current flat form with a stepper or accordion that matches the IA above.
- [ ] Extract reusable pieces into `frontend/src/components/scan/` without creating new dependencies.
- [ ] Wire validation to the existing backend `scope_guard` endpoint — do not re-implement scope logic on the client.
- [ ] All labels, help text, and error messages reviewed by the pentester persona for accuracy.

### 3.4 UX Acceptance

- [ ] First-time user (non-expert) launches a correctly-scoped scan without help in < 60 seconds (usability test with 3 participants).
- [ ] Expert user reaches advanced options in ≤ 2 clicks.
- [ ] Every control has a keyboard-accessible label; tab order is linear and sane.
- [ ] Color is never the only signal (severity also uses icon + text).
- [ ] Contrast audit (axe-core) passes WCAG 2.2 AA.

**Phase 3 Exit Criteria**
- [ ] Heuristic audit signed off.
- [ ] Wireframes approved before code changes.
- [ ] Rebuilt scan screen passes usability test and accessibility audit.
- [ ] No new backend endpoints added. No new scan capabilities added.

## Phase 4 — History Tab Reorganization (De-noise & Structure)

**Objective:** Transform the History tab from a raw log dump into a professionally organized, filterable, paginated, and scannable record of past scans.

### 4.1 Data-Model Review (read-only pass)

- [ ] Identify the backing endpoint(s) for History. Confirm it returns the fields actually needed and nothing more (over-fetching causes noise).
- [ ] Confirm a stable, indexed `created_at DESC` ordering is available at the DB layer (not sorted client-side).
- [ ] Confirm pagination is server-side; client-side slicing is a noise amplifier.

### 4.2 Visual De-Noise

Apply these rules to the existing History table/list:

1. **Column discipline.** Maximum 7 columns visible by default: Time · Target · Profile · Status · Findings (sev-tiered count) · Duration · Actions. Everything else moves to the row-expansion detail.
2. **Severity pill only.** One coloured pill per row summarizing highest severity; avoid rainbow chips everywhere.
3. **Time is relative on hover-absolute** ("2h ago", tooltip shows exact UTC).
4. **Zebra striping off; row hover on.** Striping adds visual noise; hover + subtle divider reads cleaner.
5. **Status is lexical, not emoji-only.** "Completed" / "Failed" / "Cancelled" with a left-border colour accent.
6. **Dense mode toggle** — industry-standard compact/comfortable switch (NN/g density research).

### 4.3 Filtering, Sorting, Pagination

- [ ] Filters: date range, status, profile, target (type-ahead from scan history, not free text).
- [ ] Sort: Time (default desc), Duration, Findings count. Always server-side.
- [ ] Pagination: server-side, page size 25 default, URL-synced so "back" restores state.
- [ ] Empty state, loading state, error state — all three components must exist and render correctly.
- [ ] Persist filter state in URL query params, not local state — enables sharing and deep-linking.

### 4.4 Row Expansion & Drill-Down

- [ ] Row expands inline to show: command executed, duration breakdown, finding counts by severity, link to full report.
- [ ] Clicking the row (not the expand chevron) navigates to the scan's detail view; clear visual affordance differentiates the two click targets.

### 4.5 Performance Budget

- [ ] Initial render (25 rows) < 150 ms on mid-tier hardware.
- [ ] No re-render cascade on filter change (memoize rows).
- [ ] Virtualization deferred unless default page size grows above 100.

**Phase 4 Exit Criteria**
- [ ] History tab renders with no more than 7 default columns.
- [ ] Server-side filter + sort + pagination operational and URL-synced.
- [ ] Empty / loading / error states validated.
- [ ] Perf budget met; captured in `/evidence/phase4/perf_trace.json`.

## Phase 5 — Lab Isolation & Simplified Configuration Workflow

**Objective:** Guarantee the vulnerable lab runs in a strictly isolated network and give a non-expert user a clear, repeatable path to launch a scan against it.

### 5.1 Isolation Audit (Pentester + Auditor personas)

Inspect [docker-compose.lab.yml](docker-compose.lab.yml) and [infra](infra/):

- [ ] All lab services live on a network marked `internal: true`. Verify with `docker network inspect` — `Internal: true`.
- [ ] No host port publishing on lab services (`ports:` absent; only `expose:` where needed for scanner-to-target).
- [ ] Scanner service is the only bridge: it has two NICs — one on the lab network, one on a scanner-control network. No third NIC.
- [ ] Host-level `iptables`/Windows Firewall rules deny egress from lab subnet to the internet and to the user LAN. Provide the rules as idempotent scripts under `/infra/isolation/`.
- [ ] DNS for lab services resolves only inside the lab network (no public DNS leakage).
- [ ] Outbound reachability test: from inside a lab container, `curl -m 5 https://1.1.1.1` must fail; ping to host gateway must fail. Capture output in `/evidence/phase5/egress_denied.txt`.

### 5.2 Failure-Mode Testing

- [ ] Stop/crash the scanner → lab remains isolated (no accidental bridge).
- [ ] Restart host → isolation rules re-apply (persistent, not ephemeral).
- [ ] Add a rogue container on the default bridge → cannot reach lab subnet.

### 5.3 Simplified Configuration Workflow (existing surfaces only)

The non-expert workflow, end-to-end:

1. User opens the app → sees a "Lab" panel (already exists) with status: `Up / Down / Starting`.
2. One button: **Start Lab**. Runs the existing `lab_manager` action; shows streamed progress via WS.
3. Once "Up", lab inventory auto-populates the scan screen's target dropdown (from existing lab_manager inventory).
4. User picks target → clicks scan → sees progress → sees results. No terminal, no YAML.
5. **Stop Lab** button tears down cleanly; no orphan containers, no orphan networks.

Refinements (not new features):
- [ ] Button states reflect real container state (not hopeful defaults).
- [ ] Errors from docker daemon are translated to human messages ("Docker is not running" — not a Python stack trace).
- [ ] Lab status polled on a sane interval (5–10s) or pushed via WS; never per-second.

### 5.4 Documentation

Update [HOW_TO_RUN.md](HOW_TO_RUN.md) with:
- Prerequisites checklist.
- The exact 3-click workflow above.
- How to verify isolation is active (the commands from 5.1).
- How to recover if lab starts in a half-up state.

**Phase 5 Exit Criteria**
- [ ] Network isolation verified by the egress-denied test; evidence captured.
- [ ] Isolation persists across host restart and scanner crash.
- [ ] Non-expert user (validated by dry-run with a teammate) completes Start-Lab → Scan → Stop-Lab without CLI.
- [ ] HOW_TO_RUN section updated and dated 2026-04-24.

## Phase 6 — Vulnerabilities Tab Refinement & Detection-Accuracy Audit

**Objective:** Make the Vulnerabilities tab comfortable to read under fatigue, enrich each finding with the context a SOC analyst expects, and independently verify that every planted vulnerability in the lab is detected and correctly classified.

### 6.1 Visual Refinement of Existing Tab

Audit [frontend/src/components/VulnerabilityList.jsx](frontend/src/components/VulnerabilityList.jsx):

1. **Severity-first hierarchy.** Critical and High visually dominate; Info/Low are de-saturated, not hidden.
2. **One row = one finding = one glance.** Columns: Severity · Title · Affected Asset · CVSS · First Seen · Status. Nothing else by default.
3. **Severity palette discipline.** 5 semantic colors total across the whole app (Critical/High/Med/Low/Info). No gradients, no pattern fills.
4. **Grouping toggle** (existing mechanism only): by Asset / by CVE / by Severity. No free-form grouping.
5. **Detail drawer, not a modal storm.** Selecting a row opens a right-side drawer with the enriched payload (6.2). Drawer supports keyboard nav (↑/↓ to move between findings).

### 6.2 Finding Enrichment (fields must already be produced by backend — no new scrapers)

Each finding's detail drawer shows:

- CVE ID (linked to NVD) · CWE · CVSS 3.1 vector + score · EPSS if available.
- Affected asset: hostname, IP, port, service banner.
- Detection source: scanner name, plugin/template ID, timestamp.
- Evidence: the raw scanner snippet (request/response, packet, log line) that produced the finding.
- Remediation guidance: from existing `ai_advisor` output; flagged as AI-generated.
- Duplicate/dedup info: "also seen as X other findings, grouped by `finding_dedup`".
- Validation status: `validation_probe` outcome (confirmed / unconfirmed / failed-to-probe).
- Framework mapping: from existing `framework_tagger` (MITRE ATT&CK, OWASP Top 10).

Any field the backend does not currently produce is **omitted**, not stubbed. (No new features.)

### 6.3 Alert-Fatigue Countermeasures

- [ ] Default view filters to `status != closed AND severity >= medium`. User can opt out.
- [ ] Deduplicated findings are collapsed into a single row with a count badge (already supported by `finding_dedup`).
- [ ] `validation_probe` failures are surfaced as a second-tier warning, not as a new Critical — a failed probe is not a vulnerability.
- [ ] "New since last visit" indicator uses the user's last-seen timestamp, not absolute time.

### 6.4 Scanner-Accuracy Audit (Auditor persona)

This is the single most load-bearing quality gate for the product. Execute with rigor:

1. **Build the golden dataset.** Enumerate every intentionally-vulnerable component in the lab (see `lab/`, `lab_config/`). For each, record: host, service, port, expected CVE(s), expected CWE, expected detection signature (scanner + template/plugin ID), expected severity bucket. Store as `/evidence/phase6/golden_dataset.yaml`.
2. **Freeze the lab.** Commit the lab version/image digests so the audit is reproducible.
3. **Run the full scan profile** end-to-end, via the UI (not a backdoor). Export results.
4. **Build the truth matrix.** For each golden entry:
   - **TP** — detected with correct CVE/CWE and severity bucket.
   - **FN** — planted but not detected. Each FN requires a root-cause: scanner missing plugin / template disabled / wrong scope / timeout / misparsed output.
   - **FP** — detected but no corresponding golden entry. Each FP requires a root-cause: noisy template / banner-only match / misattribution.
5. **Target metrics (industry-baseline from Phase 1).**
   - Recall on Critical/High ≥ 0.95.
   - Recall overall ≥ 0.90.
   - Precision ≥ 0.80 (FP acceptable if severity-tiered low and justified).
6. **Fix the gaps — within existing scanner configs only.** Enable the right templates, correct port lists, tune rate limits. Do **not** write a new scanner.
7. **Re-run.** Lock the numbers into `/evidence/phase6/accuracy_report.md` with before/after tables.

**Phase 6 Exit Criteria**
- [ ] Vulnerabilities tab redesigned to severity-first IA; drawer enrichment live.
- [ ] Default filters and dedup countermeasures active.
- [ ] Golden dataset committed; truth matrix produced.
- [ ] Recall/precision targets met or, where not met, each gap has a documented root cause and an accepted-risk sign-off.
- [ ] No new detection capability added — only configuration tuning within existing scanners.

## Execution Notes for the Implementing Agent

- Work phase-by-phase. Do not interleave. Phase 1's baseline document is the reference every later phase cites.
- Every change lands as a small, atomic PR tagged `stabilization/phaseN/<task>`.
- Every PR description includes: task ID from this plan, acceptance criteria evaluated, evidence path, and a one-line risk note.
- If a task appears to require a new feature to satisfy its acceptance criteria, **stop and escalate** — the constraint is that new features are forbidden, so either the criteria are wrong or the task is.
- Prefer deleting over adding. If a field, column, or route is not used, the stabilization PR is the right place to remove it.
- Do not touch files outside the scope of the current phase's task. Drive-by refactors are the enemy of a clean stabilization.
